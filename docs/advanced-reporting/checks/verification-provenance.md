# Verification run provenance

All Python tests ran in the Windows backend virtual environment. PostgreSQL checks used PostgreSQL 16 in disposable Linux Docker containers with a temporary database named `rt3_test_reporting`, a dynamic loopback-only port, random process-environment credentials, and tmpfs storage. These are integration checks, not live VPS validation.

| Artifact | Result | Scope |
| --- | --- | --- |
| `backend-postgres-combined.txt` / `.xml` | 108 passed, 1 intentional SQLite dialect skip | Initial reporting, index, export and selected existing workflow checks against SQLite/PostgreSQL. |
| `backend-final-isolated.txt` / `.xml` | 119 passed, 2 intentional dialect skips | Global bootstrap disabled and global engine in memory; reporting, recorded effort, exports, real frontend API/CSV contracts, PostgreSQL index plan and selected workflow checks. |
| `backend-verified-final.txt` | Interrupted; not a passing final result | Full existing lifecycle suite and latest zero-duration timer case were added, but Docker Desktop and its backend process stopped during this run. The PostgreSQL engine pipe disappeared. Only the exact command-verified pytest processes were stopped. |
| `backend-final-sqlite.txt` / `.xml` | 37 passed, 1 intentional dialect skip, 37 PostgreSQL variants deselected | Frozen-source full lifecycle and latest time-reporting coverage, including zero-duration timers, after Docker became unavailable. |
| `backend-postgres-recovered-final.txt` / `.xml` | 37 passed, 38 SQLite variants deselected | Frozen-source full lifecycle and all time-reporting PostgreSQL tests, including the latest zero-duration edge case, after Docker recovery. |

The first harness set the isolated PostgreSQL fixture URL but did not disable the application's global import-time bootstrap. Its initial console claim of no shared database connection was therefore too broad. A subsequent explicit read-only SQLite metadata check found all bootstrap target structures already present; the root database modification timestamp was 2026-10-20 10:21:05 UTC, earlier than that harness. No before/after hash exists for earlier standalone test imports, so this is not a claim that those imports could never have connected. All later harness runs set `VEE_BOOTSTRAP_SCHEMA=false` and `VEE_DATABASE_URL=sqlite://` before application imports and restore the original process environment afterward.

The first two completed PostgreSQL runs removed their exact created container IDs. Cleanup for the interrupted third container could not execute while the Docker API was absent. After Docker recovered, a read-only inventory found no containers with the `zeaplay.verification=advanced-reporting` label; the interrupted `--rm` helper was already absent. No unrelated containers were removed. The final recovered run recorded its exact container ID in `backend-postgres-recovered-final-container.json`, removed that exact container, and recorded `cleanup_succeeded: true`. A subsequent read-only label inventory was empty. The existing Idea Shop frontend, backend, presence, PostgreSQL and Redis containers were all running after verification.

Final result: the PostgreSQL recovery blocker is resolved. The completed 119-test combined suite covers inventory, recorded effort, exports, real frontend contracts and index planning. The final 37-test SQLite and 37-test PostgreSQL passes cover the subsequently expanded full lifecycle selection and latest zero-duration correction. These counts are separate runs with overlapping tests, not a sum of unique test cases. `backend-verification-final.json` is the consolidated machine-readable evidence manifest. The interrupted run is neither an application test failure nor a completed certification. Remaining warnings are existing SQLAlchemy/Pydantic deprecations and `datetime.utcnow()` usage; there were no failing assertions in the completed runs.
