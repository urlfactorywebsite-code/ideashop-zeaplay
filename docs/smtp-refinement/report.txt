CONFIRMED FINDINGS AND FIXES
1. Disabling a provider previously revalidated DNS and plaintext/private relay policy.
   An outage, policy revocation or missing key could prevent the safety action.
   A scoped disable-only PATCH now needs ownership/permission and the normal audit
   transaction, but no outbound resolution/secret access. Re-enabling still validates.
2. A connection reservation rejected by throttling previously overwrote a successful
   connection result as unhealthy. It now returns 429 without changing test freshness.
3. Category candidates were read before the reservation transaction. A profile could
   lose OTP authorization between selection and reservation. Current categories are
   now rechecked while locking the current profile, before any attempt/transport.
4. Quota-only cycles previously exhausted a job's retries before its daily reset.
   A blocked profile computes the later of its exceeded minute/day resets; all-quota
   cycles defer to the earliest candidate reset plus 1..3s jitter and refund only
   that non-transport claim. Real provider attempts retain their retry-budget cost.
5. Audit logging after delivery could throw and change a known accepted message to
   uncertain, or mask a known temporary error. A generic non-secret warning now
   records the audit outage without changing the SMTP result. Durable SMTP attempt
   ledger failure remains conservative/uncertain; it is not silently ignored.
6. IPv6 addresses such as 64:ff9b::7f00:1 and ::7f00:1 can be globally classified
   while embedding loopback IPv4. Effective embedded addresses are now checked too.
   Mixed DNS, mapped IPv4, peer pinning and mandatory TLS verification remain intact.
7. Servers without advertised SMTP AUTH were mislabeled as TLS failures. They now
   produce an authentication failure. STARTTLS support/certificate errors remain TLS.
8. FOR UPDATE alone was insufficient for SQLite manual retries. Retry selection now
   also performs an atomic due/state/limit conditional UPDATE. Concurrent requests
   cannot honestly report the same job selected more than once.
9. Old primary/multiple SMTP localStorage caches could survive the previous API fix.
   Startup removes those entries across API namespaces; legacy read adapters no
   longer use persisted SMTP caches. The current API never returns saved secrets.
10. Refresh discarded selections and retained old fetch-error messages. Selections
    now survive while still eligible; successful fetch clears its own error only.
    Regional edit controls reflect stored Zoho/Mailgun/SendGrid settings. SMTP toasts
    are readable above mobile navigation, while inline status/errors remain available.

SECURITY AUDIT
Authentication uses the existing signed access-token dependency and current database
user state. Missing/invalid/wrong-tenant/refresh credentials are rejected; inactive
users are rejected; signed role claims do not grant Owner powers to a database User.
Owner/Admin permission remains mandatory for all SMTP operations. Existing Manager
denial and tenant-scoped create/read/update/delete/tests/attempts/queue/health persist.
The Admin-only SMTP route does not expand access to the Owner-only OAuth/API page.

Primary/multiple credentials remain encrypted with the private Fernet keyring.
Blank replacement preserves ciphertext; nonblank replacement encrypts anew; key
rotation/adoption remain explicit operator operations. API DTOs are allowlists,
validation errors omit input values, logs use canned errors and audit field names,
and responses are no-store. Tests inspect API bodies for plaintext/ciphertext without
printing either. No saved-password visibility feature was introduced.

Public DNS destinations are validated across all answers and pinned to vetted peer
addresses. Private/loopback/unauthenticated relays require exact trusted server-side
host:port policy. Plaintext needs its separate exact exception. Link-local metadata,
multicast/unspecified and embedded restricted addresses are blocked. STARTTLS and
implicit TLS require certificate/hostname verification, minimum TLS 1.2 and the
configured CA trust. No TLS bypass was added. DNS resolution and total multi-phase
latency still have no single end-to-end deadline; egress controls remain necessary.

OPERATIONS, METRICS AND DUPLICATE POLICY
Create uses POST; edit/enable/disable uses PATCH; cancel discards the draft. Busy
action guards and database uniqueness prevent duplicate clicks/creation. Connection
test opens/authenticates without DATA. Send Test requires an explicit recipient/action.
HTTP failure cannot produce success feedback. A generic 5xx/network failure may occur
after acceptance: inspect attempt/provider logs before requesting another test.

Health is not enabled status: a successful connection/auth test is healthy <=15m,
degraded at 15..60m, failed recent tests unhealthy, missing/>60m untested; disabled
overrides. A settings revision race cannot mark newly edited settings healthy. A
throttled reservation leaves the last real test untouched.

Attempt analytics use the selected UTC window by start time. Queue counts are current
tenant job states across all time. Accepted means final SMTP 250, not inbox delivery.
Failed attempts are known temporary/permanent transport failures, not failed jobs.
Success is accepted/(accepted+failed), null with no denominator; uncertain/reserved
and connection tests are excluded. Processing duration excludes queue waiting and
downstream delivery. All message reservations, including tests/failures/uncertainty,
count toward profile quotas. Explicit tests and deleted profile history are included.
profile_stats now includes retained keys plus current profiles; retired_profile_keys
identifies those absent from the current list. The UI displays their accepted/failed
subtotal. Overall counts equal current plus retired groups for the SAME window.

The existing persistent outbox remains in use. Canonical categories, exact-category
priority ordering, same-tenant general fallback and OTP-only explicit routing remain.
Quota-only waits defer without transmitting; configuration/temporary transport errors
retain bounded retries with backoff/jitter. Permanent recipient/content failures stay
terminal. Ambiguous DATA acceptance, unknown transport/ledger outcomes and stale
sending jobs are held without automatic resend/failover. Manual retry is due-only,
tenant-scoped and atomic; it cannot reset attempts/quotas or replay uncertain jobs.
SMTP is not exactly-once. A stable Message-ID assists investigation, not deduplication.

Existing welcome, ticket and password-recovery outbox workflows were exercised.
The system-reset OTP REQUEST route was tested through mock SMTP; the destructive
reset confirmation/execution routes were never invoked. Application login, token
generation and ticket permission tests passed. This does not prove every unrelated
application page or a full deployment is regression-free.

SAFE DEPLOYMENT AND REMAINING RISKS
No new migration is required for this refinement. It still requires the prior SMTP
schema revision ff7a8b9c0d1e after fe6f7a8b9c0d and the coordinated API/UI contract.
Use the existing detailed runbook at ../smtp-management/implementation-and-runbook.txt.
Do not deploy this source over an unreconciled legacy database or stamp it to head.
The previously observed local application lacked an Alembic baseline; this task did
not inspect secret values or modify that database to resolve the gate.

1. Inventory actual schema/revision and pending jobs without password columns; take
   a verified backup and rehearse restore/migration against an isolated copy.
2. Quiesce all backend/mail workers; retain old image IDs. Set bootstrap false and
   SMTP delivery false in the private server environment. Resolve a missing baseline
   through a reviewed schema reconciliation, not create_all or blind historical DDL.
3. Apply/rehearse the prior Alembic migration only from a compatible baseline.
   Provision the dedicated private keyring outside Git/VITE/browser config.
4. Explicitly map/adopt legacy profiles to reviewed tenants, encrypt them and keep
   them disabled. Review sender identities, OTP categories, provider auth and quotas.
   Old unowned plaintext remains a database/backup risk until adoption/retirement;
   rotate credentials potentially exposed by the former API/caches. Cache cleanup
   cannot undo credentials already copied or exported by an old client.
5. Deploy coordinated new API/UI while delivery is disabled. Verify permissions,
   non-secret CRUD, quota/health definitions and no-store responses. Keep destination
   exceptions empty unless an operator approves the exact relay.
6. Review queued mail before enabling delivery/profiles. Enabling normal workers can
   release queued workflow messages. An external provider test still needs an
   explicitly approved recipient/action; none was sent here. Check provider logs,
   SPF/DKIM/DMARC, TLS/network policy and authentication with actual account operators.
7. On failure disable delivery and quiesce workers. Prefer a compatible forward fix;
   do not run the old global/plaintext backend against adopted encrypted rows. Prior
   downgrade guards refuse populated history/owned secrets. A full restore requires
   reconciling mail accepted/uncertain since the backup before any replay.

Remaining: SMTP OAuth/token lifecycle; real provider and inbox confirmation; live
schema/key/adoption/deployment verification; full Linux suite, long-duration load and
memory/latency measurements; DNS/whole-operation deadlines and site egress controls;
SMTP attempt retention/archiving. Custom NAT64/routing policies also need network
egress enforcement. Sustained exhausted quotas can leave mail waiting; monitor age
and capacity. No claim of perfect accessibility or exhaustive unrelated-app coverage:
screen-reader assistive-technology/manual provider tests were not performed.
